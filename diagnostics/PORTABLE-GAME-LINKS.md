# Этап 2: игровые ссылки таблиц `game.db`

Типизированные объекты `game.db` пока создаёт Windows-часть. Первым
проверяемым игровым ребром выбран `Animations.SkeletonID` (таблица 2 →
`Skeletons`, таблица 13): `BuildMapLinks` группирует эти анимации по
скелету, а игра затем выбирает анимацию из группы. Редакторские связи
сюда не входят.

`FileIO/PortableGameLinks.{h,cpp}` извлекает пары `(animation ID,
skeleton ID)` из декодированных переносимым загрузчиком колонок,
проверяет дубликаты ID, форму строк и наличие целевых скелетов. Для
сравнения с объектным графом пары хешируются в отсортированном порядке,
без зависимости от обхода `unordered_map`. Отдельный `order-hash` оставляет
порядок обхода неизменным. `PortableGameDatabaseProbe game.db --links`
выводит число ссылок, отсутствующие цели и оба хеша.

Оригинальная `G:\SS\lab\baseline\game.db` (SHA-256
`314d7aa9e6339f0e6826bf2a0c71fdad992aec1d6074a2ed763a6f6fa62d62df`)
дала `animation-skeleton-links 2045 unresolved 0 hash
4fa2d472a44bace6` на Windows x64, Linux x86-64 и ARM64/QEMU.
На двух Linux-архитектурах декодер и синтетический
`PortableGameLinksTests` прошли с ASan/UBSan (`detect_leaks=0`).
Временная копия лицензированной базы после сверки удалена с Linux-хоста,
локальный оригинал остался нетронутым.

Игровой `BuildMapLinks` при `S2_DB_PARITY=1` теперь считает такой же
порядконезависимый хеш уже разрешённых указателей `CAnimation::pSkeleton`.
Чистый архив `stage2-game-links-20260924-01` (коммит `2a82848`,
нативные звук/видео) в запуске `stage2-game-links-clean-01` вывел
`DB-PARITY animation-skeleton-links=2045 hash=4fa2d472a44bace6`.
Старая запись `DB_OLD` загрузилась до `LOAD-SLOT-DONE`, после `quit`
игра и отладчик завершились без дампа. Windows x64 CTest — 26/26.
Весь переносимый CMake-набор из того же коммита `2a82848` собран на
Linux x86-64 и ARM64/QEMU с ASan/UBSan: по 15/15 CTest на каждой
архитектуре (`detect_leaks=0`). Это модульные/контрактные тесты,
не сборка Linux/ARM64 игры.
Так доказано совпадение множества ссылок для этой таблицы, но не порядок
анимаций внутри скелетных групп, не остальные ссылки и не полный
паритет выбора анимации с розничным x86.

Аудит порядка (2026-09-24): исходный `game.db` дал `order-hash
4fa2d472a44bace6`, то есть порядок его 2045 ссылок совпал с
сортировкой пар по ID. В диагностическом x64-прогоне
`stage2-game-links-order-dev-01` множество то же, но порядок обхода
`unordered_map` другой: `order-hash b42e9fcf49308232`. Это само по себе
не затрагивает выбор анимации, если перемешаны лишь разные группы.
Поэтому следующий прогон `stage2-game-links-groups-dev-01` проверил
каждую группу `(SkeletonID, Type)` отдельно: 455 групп, 367 переходов
к меньшему ID внутри одной группы; первый — SkeletonID 8, type 44.
`SAnimationVector::GetAnimation` перебирает группу в таком порядке,
поэтому возможен иной результат при одинаковом состоянии генератора
случайных чисел или равных весах. Это диагностическая находка, не
доказанный регресс относительно розничного x86: его групповой порядок
ещё надо сравнить, прежде чем менять игровую сборку ссылок. Оба прогона
были dev-запусками с заменёнными Game.exe/PDB поверх чистого архива,
не воспроизводимыми чистыми архивами; граф связей не менялся.
Попытка собрать текущий x86 Game для того же прогона остановилась на
линковке: старый x86-проект ожидает `__fastcall`-символы переносимых
библиотек, а библиотеки их не предоставляют. Это не результат проверки
порядка на x86 и не регресс x64; 32-битная конфигурация больше не цель
реставрации. Исторический чистый x86-архив остаётся пригоден для
ограниченных обратных проверок сейвов, но в нём нет этой диагностики.

Продолжение 2026-09-25: исходный январский `DataMap.cpp` действительно
добавляет анимации в вектор при обходе `CDBIterator`, а `BasicDB.h`
хранит записи в `std::hash_map`. В поставленном вместе с исходниками
STLport (`stl/_hash_map.h`, `stl/_hashtable.c`, `stl/_hash_fun.h`)
карта по умолчанию начинает с 193 бакетов, `hash<int>` возвращает ID,
добавление ставит элемент в начало цепочки, расширение повторно
перекладывает цепочки в начало новых бакетов. Переносимый пробник
воспроизводит этот алгоритм **только для диагностики**; поскольку все
2045 строк `Animations` данной базы имеют `SkeletonID`, входной список
содержит все вставки карты. Это модель поведения исторического исходника,
не прямое измерение Steam EXE.

Группы `(SkeletonID, Type)` теперь сравниваются по последовательностям
ID внутри каждой группы, а сами группы упорядочиваются по их минимальному
ID для хеширования: не нужно дублировать числовой enum типов в пробнике.
Оригинальный `game.db` дал 455 групп и хеш `e2f7fe89cbcf0d6c` при
порядке строк, модель STLport — те же 455 групп и
`63aff1ef63fac020` (`order-hash` всех ссылок `36e5e15fd45de252`).
Диагностический x64-запуск `stage2-game-links-hash-dev-01` дал те же
455 групп, но хеш `d47a85ffe0bc1dd8` и прежние 367 инверсий.
Это показывает отличие нынешнего обхода `unordered_map` от обеих моделей.
Перед изменением порядка в игре нужна прямая проверка на оригинальном
x86 EXE или эквивалентное подтверждение его конкретной реализации;
контрактный тест исходников сам по себе недостаточен. Dev-запуск завершился
после `quit` без crash dump; Windows x64 CTest — 26/26.
`dbh` подтвердил наличие `NDb::BuildMapLinks` в private PDB RussianGold
по RVA `0x416e60`, но это проверка символа, не порядка значений в памяти.
Новый переносимый код и весь набор CTest прошли на Linux x86-64 и
ARM64/QEMU под ASan/UBSan (`detect_leaks=0`), по 15/15. Пробник на
оригинальной базе выдал на обеих архитектурах те же три хеша групп и
`order-hash` модели STLport, что на Windows x64. Временная копия
`game.db` на Linux-хосте удалена, локальный оригинал не изменён.

Прямая x86-сверка (2026-09-25) сняла прежнее ограничение: Steam
`game.exe` сборки 122676 (SHA-256
`4f417593a9f73e2bfde12d83cdbd694ae47eecb92812140d67b8b343e4a95705`)
работает на изолированной копии тех же данных. Совпадение 242 из первых
256 байт `BuildMapLinks` с `RussianGold` указало на RVA `0x405980` в
Steam EXE. Отладчик остановился после получения таблицы `Animations`
на RVA `0x4059e9`: её хеш-таблица имела 3079 бакетов и 2045 записей.
Скрипт [retail-animation-order.cdb](retail-animation-order.cdb) выгрузил
все 2045 ID в порядке реального обхода цепочек. Пробник с опцией
`--oracle-order` проверяет полноту/уникальность ID и собирает группы
по исходному `game.db`: `order-hash 36e5e15fd45de252`, 455 групп,
`group-hash 63aff1ef63fac020`. Оба хеша точно совпали с переносимой
моделью STLport. Повторный запуск скрипта также вывел 2045 ID (лог
`G:\SS\lab\runs\retail-steam-oracle-01\evidence\dump-animation-order-repro.log`,
SHA-256 `bf5b44921c43c63a11eacf9436793852109f4cfe474c0f79f2a0e59a11cb04b1`).
Это наблюдение оригинального Steam x86, а не только исходниковый контракт.

`RussianGold Game.exe` с private PDB на данном изолированном комплекте
не дошёл до импорта: системное окно сообщило об отсутствующем экспорте
`_FSOUND_Stream_AddSynchPoint@12` в комплектной `fmod.dll`. Этот запуск
завершён; ошибка не относится к восстановленному x64 или рабочему Steam
EXE. Копия данных и DLL оставалась в `lab/runs`, оригинальная установка
не изменялась.

Игровой v1-загрузчик теперь передаёт в `BuildMapLinks` полный порядок
ID строк `Animations`; переносимая функция воспроизводит обход
исторического `hash_map`, а текущая Windows-таблица находит готовые
объекты по ID. Путь редактора/старого v0 без колонночного порядка не
менялся. В dev-запуске `stage2-animation-order-dev-01` x64 Game вывел
те же 2045 ссылок и оба хеша, что прямой Steam x86-эталон; старый слот
`DB_OLD` загрузился до `LOAD-SLOT-DONE`, затем `quit` завершил оба
процесса без crash dump. Windows x64 CTest — 26/26. После правки
Linux x86-64 и ARM64/QEMU под ASan/UBSan прошли по 15/15 тестов;
на исходном `game.db` оба пробника повторили прямой x86-эталон:
2045 ссылок, `order-hash 36e5e15fd45de252`, 455 групп и
`group-hash 63aff1ef63fac020`. Временные копии базы и лога эталона
на Linux-хосте удалены. Для полного закрытия этого игрового пути
ещё нужен чистый архив.

Воспроизведение сравнения на стенде (только изолированная копия Steam
EXE указанного SHA-256, не исходная установка):

```powershell
$run='G:\SS\lab\runs\retail-steam-oracle-01'
$cdb='C:\Program Files (x86)\Windows Kits\10\Debuggers\x86\cdb.exe'
& $cdb -G -o -logo "$run\evidence\dump-animation-order-repro.log" -cf .\diagnostics\retail-animation-order.cdb "$run\game\Game.exe" -windowed -800
& G:\SS\lab\build-x64\RelWithDebInfo\PortableGameDatabaseProbe.exe G:\SS\lab\baseline\game.db --oracle-order "$run\evidence\dump-animation-order-repro.log"
```

Воспроизведение чтения данных на этом стенде:

```powershell
& G:\SS\lab\build-x64\RelWithDebInfo\PortableGameDatabaseProbe.exe G:\SS\lab\baseline\game.db --links
```

Для чистого игрового прогона включить `S2_DB_PARITY=1` перед запуском
`Start-LabRun.ps1`; искомая строка находится в `evidence/debugger.log`.
