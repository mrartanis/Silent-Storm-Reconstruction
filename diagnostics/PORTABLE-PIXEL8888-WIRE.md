# Этап 2: четырёхканальный цвет в игровых данных

Миссионный raw-аудит обнаружил `NGfx::SPixel8888` — 13 646 записей
по путям загрузки и повторной загрузки сохранения. Тип используется
игровыми эффектами, интерфейсом и миниатюрами сохранений, не только
редактором.

`FileIO/PortablePixel8888Wire.h` задаёт четырёхбайтный порядок
B, G, R, A для формата `CF_A8R8G8B8`. Специализация в
`Main/GPixelFormat.h` перекладывает каналы через упакованное 32-битное
значение, не копируя память структуры как дисковый формат.
`PortablePixel8888WireTests` проверяет точные байты и длины;
расширенный `NativeZoneWireTests` сравнивает результат с MSVC x86/x64.

На 2026-09-25 Windows x64 CTest 50/50, Linux x86-64 и ARM64/QEMU
под ASan/UBSan по 30/30, целевые диагностические x86-тесты 2/2.
Чистый x64-архив `stage2-pixel8888-wire-20260925-01` загрузил старый
миссионный слот `stational weapons`, записал `PIXEL8888_NEW` и
открыл его повторно (`LOAD-SLOT-DONE` оба раза). Точный тип исчез
из `_wireaudit.log`, дампа нет. Чистый архив восстановленной
x86-сборки `stage2-pixel8888-wire-x86-20260925-01` прочитал новый
слот до `LOAD-SLOT-DONE` без дампа. Артефакты запусков:
`C:\SS-lab\runs\stage2-pixel8888-wire-clean-01` и
`C:\SS-lab\runs\stage2-pixel8888-wire-x86-clean-01`.

Оба запуска использовали `New-LabRun.ps1 -LinkResources` для чтения
одного baseline `res` без повторного копирования. В `run.json`
зафиксирована junction-цель; после прогонов SHA-256 всех 23 `.res`
совпали с `G:\SS\lab\evidence\baseline-files.csv` (23/23).
Само представление `SPixel8888` с битовыми полями остаётся частью
старого графического кода; перенос дисковой записи не означает переход рендера на bgfx
и не доказывает паритет изображения со Steam.
