# Индексный GPU-буфер: реализация и проверка, 2026-10-03

## Результат

CPU-кольцо осталось 64 KiB. Его последовательные снимки теперь размещаются
в разных областях одного GPU-банка размером до 4 MiB. На исследованном сейве
пересоздания индексного GPU-буфера сократились с ~49 за кадр до практически
нуля. Существенный прирост FPS от этого изменения не подтвердился.

| Камера, 2560×1440 | Прежнее поведение | Дописывание на GPU |
|---|---:|---:|
| Сильное отдаление, rod=80 | 62.78 FPS | 63.28 FPS |
| rod=50 | 86.06 FPS | 86.02 FPS |
| Дома, rod=50 | 65.68 FPS | 65.57 FPS |

Таблица объединяет два отдельных запуска каждой версии поведения, 300 и
600 кадров на позицию, через среднее время между кадрами. В первой паре
rod=80 получилось 63.64→62.83 FPS, во второй 62.35→63.51 FPS. Направление
маленькой разницы меняется между запусками: её нельзя объявлять устойчивым
ускорением. Анимация и симуляция активны; зафиксирована только камера.

Ожидаемый большой выигрыш от устранения пересозданий не подтвердился.
`geometry_rename_ms` включает также сброс и упаковку VB: это не стоимость
только индексных allocations. На rod=80 общий интервал сократился
1.373→1.098 мс, а оставшаяся упаковка вершин занимает 2.526 мс.

## Реализация

- `BgfxBuffer` сохраняет признак динамического индексного буфера из usage.
  Большие GPU-банки выделяются для динамических IB с поддержкой смещения
  привязки; обычные статические IB сохраняют прежний размер.
- При конфликтующей записи в CPU-кольцо queued draw и изменённые блоки
  прежнего окна сбрасываются. Новые данные занимают следующее GPU-окно,
  `QueueDraw` получает смещённый первый индекс. Ранние draw продолжают
  использовать свои неизменные данные.
- При заполнении GPU-банка остаётся прежний безопасный механизм snapshot:
  старый handle освобождается через bgfx, создаётся новый. Более тяжёлые карты
  могут использовать этот путь; 4 MiB не являются пределом геометрии кадра.
- При следующем GPU-кадре окно возвращается в начало и сбрасываются версии
  блоков старого окна. Устройство/epoch обрабатываются прежним GPUStorage.
- `NextFrameBuffes(true)` старит кеш геометрии, но больше не перематывает
  индексное кольцо внутри того же GPU-кадра. Обычный конец кадра перематывает.
  `OnThrashing` по-прежнему сбрасывает отложенные 32-bit примитивы до старения.
- Дополнительная ёмкость активного индексного GPU-банка — около 3.94 MiB;
  CPU-кольцо и его block metadata остаются маленькими. При переполнении
  несколько GPU-банков могут временно сосуществовать до завершения draws.

Диагностические переменные:

- `S2_GEOMETRY_INDEX_NO_APPEND=1` отключает дописывание в GPU-окна.
- `S2_GEOMETRY_INDEX_REWIND_ON_THRASH=1` возвращает перемотку при старении кеша.
  Вместе эти два флага воспроизводят прежнее поведение для A/B.
- `S2_GEOMETRY_INDEX_KB=64..16384` меняет CPU-кольцо, default=64.

## Почему просто большой CPU-буфер не оставлен

Прямое увеличение CPU-кольца проверено отдельной серией в одном EXE:

| CPU-кольцо | rod=80 | rod=50 | Дома |
|---|---:|---:|---:|
| 64 KiB, прежняя перемотка | 63.23 | 86.33 | 65.79 |
| 128 KiB, без лишней перемотки | 62.47 | 85.17 | 64.25 |
| 256 KiB, без лишней перемотки | 62.23 | 85.46 | 65.74 |
| 512 KiB, без лишней перемотки | 60.61 | 80.73 | 64.26 |
| 4096 KiB, без лишней перемотки | 59.65 | 78.54 | 62.57 |

У 4 MiB почти нет пересозданий, однако FPS ниже; `present_ms` на rod=80
увеличился 1.493→1.943 мс. Удаление allocations само по себе не устраняет
подготовку индексов, загрузки и работу backend. Конкретная причина всей
регрессии большого CPU-кольца этими замерами отдельно не установлена.
Итоговый вариант сохраняет маленькие CPU-порции и устраняет allocations
через размещение на GPU. GPU updates остаются примерно 49 за кадр: количество
пересозданий и количество загрузок — разные метрики.

Ранние `ring64`/`ring4096` прогоны НЕ являются проверкой большого активного
буфера: первая версия увеличивала только 32-bit ветку, тогда как игра
использует 16-bit (`bBan32BitIndices=true`). Их EXE и результаты сохранены
для аудита, но в таблицы сравнения они не включены. `active4096` — отдельный
промежуточный вариант с ещё сохранённой перемоткой при старении кеша.

## Проверки

Сборка Game и BgfxRendererTests успешна. Новый `--index-ring` проверяет
16- и 32-bit пути: старение кеша внутри кадра, заполнение маленького CPU-кольца,
дописанные GPU-окна, принудительное переполнение многомегабайтного GPU-банка,
сохранность раннего красного draw, позднего зелёного draw и повторное
использование банка в следующем кадре. Проверяются пиксели и счётчики.
В CTest зарегистрирован `IndexRingRuntimeTests` с CPU-кольцом 64 KiB.

Пройдены все режимы renderer regression: основной, `--geometry`, `--partial`,
`--index-ring`, `--passes`, `--graphics`, `--display`, а также 300 parity cases
IndexBoundsBench. Журналы: `G:/SS/lab/index-final-test-*.log`,
`index-final-parity.log`, `index-gpuappend-build.log`.

Финальный игровой harness: 900 кадров во время 24 pan/zoom команд,
rod=60..130, смена 2K→1080p→2K, ещё 120 и 180 проверенных кадров после
переходов, save/load отдельного тестового слота, screenshots. Все собственные
игровые процессы завершены через `quit`, exit code=0. Пользовательские saves
изолированы от тестовых.

## Оценка пункта 2

Компактный GPU-формат остаётся следующим разумным экспериментом. В итоговом
rod=80 кадре упаковываются ~93 тысячи вершин, около 7.1 MB выходных данных,
на CPU это занимает ~2.5 мс. Основной Full-формат расширяется 32→76 байт.
Прямая загрузка компактных атрибутов может убрать часть преобразований и
уменьшить объём данных. Эти 2.5 мс нельзя целиком обещать как будущий выигрыш:
копирование, snapshots и uploads останутся.

Потребуется проверка BGRA swizzle, signed SHORT2 UV без изменения масштаба,
нормалей, tangent/bitangent, lightmap, bump, теней и UI. Нативный D3D11
Int16 без normalization отображается в SINT; его совместимость с входами
shader необходимо проверить, а не предполагать. Формат вершин и shaders
в этом изменении не менялись. Пункт 2 ещё не реализован.
