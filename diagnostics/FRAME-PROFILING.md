# Профилирование времени кадра

Исследование 2026-10-02 воспроизвело около 20 FPS на карте с шестью бойцами и
зданиями в 2560×1440. Главная измеренная стоимость — преобразование вершин на
основном потоке в `BgfxDeclaration::CopyVertices`. При дальнейшем отдалении она
растёт вместе с числом отправленных объектов. В редакторе отдельно обнаружена
повторная генерация неизменной формы FaceGen; на FPS исследованной карты лица
влияют мало.

## Выполненные оптимизации 1, 2 и 4

По решению пользователя выполнены пункты 1, 2 и затем 4. Пункт 3 (FaceGen)
исключён: игровая анимация лиц не изменена. Диагностическая заморозка остаётся
только явно вызываемой harness-командой.

На той же миссии, с фиксированной камерой rod=80, 2560×1440, VSync=0:

Каждый замер — отдельный процесс, 180 представленных кадров после прогрева,
с одинаковыми якорем/yaw/pitch/rod. Анимация и временные проходы продолжают работать,
поэтому число draws и распределение времени немного меняются между прогонами.
Для итоговых прогонов бюджет transient не переопределён: штатные 64/16 MiB.
Для исходного renderer и этапов 1/2 использовался диагностический бюджет 256/64 MiB.
Итог: около 3,3× исходного FPS на большом отзуме. Эффект batching на FPS умеренный
(примерно 4–6% в A/B), основной выигрыш дают пункты 1 и 2.

Пункт 4 объединяет около 1222–1262 draws за кадр: число GPU draws уменьшается
примерно с 3735 до 2500 (около 33%). Он сохраняет исходный порядок, объединяя только
соседние совместимые диапазоны. Изменение constants, shaders, textures, sampler,
render state, render target, Clear, FXAA и завершение кадра ставят барьер.
Line strips не объединяются. Удалено лишнее выравнивание 32-битных треугольников,
которое создавало пробелы между диапазонами; 16-битное выравнивание сохранено.

На прежнем масштабе rod=50 миссия даёт **62,36 FPS** вместо исходных 20,00,
работа кадра 15,93 мс. Штаб rod=50: **108,42 FPS**, 9,13 мс (его исходная камера
в раннем замере не фиксировалась, поэтому точный A/B для штаба не заявляется).
Расширенный редактор: 5,39 мс против прежних 5,53 мс; генерация лица не оптимизирована.

### Как работает хранение геометрии

- Declaration один раз декодирует фактические атрибуты. Упаковщик копирует float,
  переводит signed short в float и нормализует BGRA в RGBA напрямую.
- GPU vertex bank различается по identity declaration, смещению stream и stride.
  CPU Unlock инвалидирует написанные страницы; pooled geometry сообщает точные
  диапазоны, а неизвестные записи инвалидируют весь диапазон Lock. Readonly Lock
  ничего не инвалидирует. CPU staging сохранён для старого движка.
- Изменённые блоки (128 вершин / 256 индексов) сохраняются в снимке банка. Соседние
  блоки загружаются одним update перед `bgfx::frame`, без тысяч мелких загрузок.
  Если движок перезаписал данные, уже использованные в текущем кадре, старый банк
  сначала загружается и получает отложенное уничтожение, а новый получает другой
  GPU handle. Это сохраняет ранние draws: bgfx применяет dynamic updates до draws.
- Банки привязаны к epoch устройства. При новом renderer они пересоздаются, старые
  handles не уничтожаются в новом устройстве. Resize сохраняет действующие банки.
- В окончательном большом отзуме упаковывается около 7,1 MB вершин за кадр вместо
  39,6 MB. Общие GPU geometry uploads с индексами — около 9,8 MB. Примерно 123 VB
  updates и 50 IB updates вместо пробного варианта с более чем 9000 IB updates.
  Цена — дополнительный CPU снимок и постоянные GPU allocations, освобождаемые
  вместе с буфером; геометрия остаётся ограничена существующими пулами движка.

### Проверки и материалы реализации

`VertexPackingBench` теперь сравнивает **живой** упаковщик с сохранённым исходным
универсальным кодом. Проверены три игровые declarations и declaration с пропусками
во входных данных, все 65536 signed-short значений, все color bytes и finite floats,
включая -0.0. Выходные данные побитово совпали. Для 65536 вершин × 40 повторов:
full 219,08→73,17 мс (2,99×), tc 130,10→21,40 мс (6,08×),
nt 132,18→8,73 мс (15,14×), padded 131,20→27,58 мс (4,76×).

неизменённых/readonly данных, раздельные записи в один блок pooled buffer,

base vertex, indexed/nonindexed batching, барьеры constants, ненулевой stream offset
и пересоздание renderer с живыми CPU буферами. Обычные renderer tests проверяют
depth, stencil, blend, alpha, targets, pass order, texture upload, readback и resize.

## Исходное исследование: условия и результаты

Windows x64, RelWithDebInfo, Intel i5-14600K (20 логических потоков), RTX 3070 Ti,
bgfx Direct3D 11. VSync отключён. Данные и сохранения скопированы в отдельный
лабораторный запуск; пользовательские игры не использовались и не закрывались.
Каждый замер содержит 180 или 240 представленных кадров после прогрева.

|---|---:|---:|---:|---:|

| Карта миссии, штатный буфер, камера около 50 | 47,51 | 31,69 | 0,51 | 9,13 |
| Та же карта, лица заморожены | 47,23 | 32,17 | 0 | 9,91 |
| Миссия, фиксированная камера 50, 2560×1440 | 49,80 | 34,32 | 0,19 | 12,65 |

| Камера 80, лица заморожены | 68,26 | 47,71 | 0 | 17,85 |

Фиксированные камеры проверены через `camerastatus` (`frozen=1`); якорь, pitch и
yaw сохранялись. Серия фиксированных камер использовала диагностический бюджет
256/64 MiB вместо штатных 64/16 MiB для временных вершин/индексов. Это отдельный
контрольный режим, не изменение штатных настроек. FPS по интервалу начала кадров:
20,00 при rod=50; 14,75 при rod=80; 14,62 при rod=80 с замороженными лицами.
В 1280×720 получено 20,49 и 15,28 FPS соответственно: уменьшение числа пикселей
в четыре раза существенно не устраняет ограничение на CPU.

При rod=80 отправляется около 3788 draw calls, 332 упорядоченных проходов и
519 тысяч преобразованных вершин (39,4 MB данных вершин) за кадр. Это объём
повторно отправленной геометрии, включая несколько проходов, а не число уникальных
вершин карты. Упаковка занимает около 70% работы кадра. Ожидание submit в статистике
bgfx согласуется с простоем рендер-потока в ожидании основного потока; общая низкая
загрузка многоядерного CPU не исключает такое ограничение.

## Исходные предложения (до реализации)

Ниже сохранены предложения первоначального исследования. Актуальная реализация
и её проверки описаны выше; первоначальный пункт 3 исключён пользователем.

1. **Ускорить `CopyVertices`.** Сейчас каждый draw повторно обходит все возможные
   атрибуты для каждой вершины, декодирует layout и вызывает универсальные
   `vertexUnpack`/`vertexPack`. Подготовить offsets/types один раз в declaration и
   использовать прямые копирования float, преобразования short→float и BGRA→RGBA.
   Диагностический `VertexPackingBench` сравнивает прототип с текущим кодом на
   трёх игровых форматах. Для 65536 вершин × 40 повторов получено:
   full 202,43→71,43 мс (2,83×), tc 123,71→34,98 мс (3,54×),
   nt 122,91→37,26 мс (3,30×), с побитовым совпадением выходных буферов.
   Прототип находится только в benchmark; игровой упаковщик ещё не заменён.
   Перед внедрением проверить все реально встречающиеся declarations, смещения,
   короткие индексы и кадры игры. Ускорение микробенчмарка не равно ускорению FPS.
2. **Переиспользовать геометрию между проходами и кадрами.** Статические здания и
   terrain не должны каждый кадр целиком конвертироваться в float и копироваться
   в transient buffers. Следующий шаг — GPU vertex/index buffers и draw ranges;
   динамические головы/скиннинг обновлять по версии данных. Нужна корректная
   инвалидизация при разрушениях, Unlock, изменении layout, resize и смене устройства.
   До постоянных GPU буферов возможен кэш преобразования по версии CPU буфера и
   declaration, но он сохранит лишние загрузки в transient buffer.
3. **Кэшировать неизменный FaceGen.** В редакторе `CHeadTransformInfo::NeedUpdate`
   реагирует на время; `Recalc` каждый кадр вызывает `Generate` и для геометрии, и
   для texture-weight rig. В повторном замере Generate занимает 3,83 мс, включая
   1,15 мс blend, 0,63 мс compose и 0,23 мс выбор весов. Остальное включает
   сборку animators, обработку мышц и вспомогательные копирования. Кэшировать
   результат по изменению tensions/исходного rig; анимация моргания и речи должна
   продолжать обновляться отдельно в `CHeadAnimator`. Фактическое запекание
   текстуры уже проверяет tension stamp — оптимизировать нужно прежде всего
   повторный Generate его весов. Проверить существующие FaceGen/idle/sequence
   parity fixtures, изменения sliders и save/load. Сильные тормоза редактора,
   описанные пользователем, на этих данных не воспроизведены.
4. **После повторных замеров заняться количеством draw calls.** Отдельные
   кандидаты — переиспользование static ranges, объединение совместимых draws и
   culling объектов/теневых проходов. Стоимость упаковки уже измерена; эффект
   batching и дополнительного culling пока не измерен.

## Ограничения и обнаруженные ошибки

- В нескольких подготовительных прогонах рендер выдавал `Transient game geometry
  budget exhausted` или `Game exceeded ordered render-pass limit` и переставал
  представлять кадры. Эти CSV исключены: ноль presents не является высоким FPS.
  Исчерпание ресурса делает backend unhealthy до перезапуска. Следует отдельно
  исправить управление бюджетами и восстановление после ошибки; просто увеличивать
  лимит без устранения повторных загрузок — временная мера.
- rod=120 со штатной дальностью отсечения даёт почти чёрный кадр с фрагментом карты.
  Его формально более высокий FPS не считается улучшением: представительная
  геометрия исчезла. Результат сохранён как диагностика камеры/отсечения.
- Ранние незамороженные камеры могли двигаться; выводы о масштабировании основаны
  на серии фиксированных камер. Начальные CSV `mission_final_720` содержат неверно
  названный `frame_interval_ms`, взятый из асинхронной статистики bgfx. Для них
  использовать `frame_ms`; окончательная серия `fixed*` измеряет интервал собственными
  часами. Никакой вывод не основан на ошибочном значении FPS той ранней серии.
- Средние GPU значения относятся к предыдущим асинхронным кадрам. CPU scopes
  вложенные и включают дочерние scopes: нельзя складывать scene, submit и
  vertex_pack. В `head_ms` не входит отдельный morph scope из UI.
- Не исследованы все карты кампании, предел масштабирования на больших картах,
  физические Linux GPU и поведение с большим числом разговаривающих персонажей.

## Использование инструментов

Собрать `Game` и `VertexPackingBench` обычной конфигурацией проекта. В `-harness`
доступны команды:

```text
perf <ASCII-tag> <1..10000 frames>
perfstatus
perffaces 0
perffaces 1
perfzoom <5..150 rod>
perfbasicfacegen
```

`perf` сохраняет `_perf_<tag>.csv` в рабочий каталог игры и отказывается
перезаписывать существующий файл. `perffaces 0` диагностически замораживает
обновление уже построенных голов и морфа; это не предлагаемое игровое поведение.
`perfzoom` фиксирует камеру, сохраняя её якорь и ориентацию, и задаёт точный rod.
Не сохранять такое состояние в пользовательский слот. При обычном запуске
профилирование выключено. Состояние scopes локально для потока: измеряются
основной поток и вызванная им native LifeStudio, а не работа resource workers.

`ProfileFrames.py` запускает собственную игру в подготовленном `New-LabRun`
каталоге с отдельным `S2_USER_DATA_DIR`, исполняет JSON-план, собирает CSV,
сохраняет observations/summary в evidence и завершает процесс через `quit`.
План состоит из `command`, `wait` и `capture`:

```json
[
  {"command": "load stage6_entered_mission_fixture"},
  {"wait": 5},
  {"command": "perfzoom 80"},
  {"wait": 2},
  {"command": "camerastatus"},
  {"capture": "map80", "frames": 180},
  {"command": "perffaces 0"},
  {"wait": 2},
  {"capture": "map80_frozen", "frames": 180},
  {"command": "screenshot"}
]
```

Слот должен находиться в изолированном user-data. Между картой и модальным
редактором предпочтительны отдельные процессы: не загружать другую карту поверх
модального редактора. Не запускать два драйвера на одном каталоге одновременно.
Для wide-view stress можно явно установить `S2_PERF_TRANSIENT_MB=256` в окружении
дочерней игры; разрешён диапазон 64..512 MiB, IB budget = VB/4.
Постоянные GPU буферы включены по умолчанию. Для диагностического A/B установить
`S2_GEOMETRY_TRANSIENT=1`, чтобы вернуть transient путь с быстрым упаковщиком,
или `S2_GEOMETRY_NO_BATCH=1`, чтобы отключить объединение draws. При снятии этих
переменных используются все реализованные оптимизации.

`G:/SS/lab/runs/perf-investigation-20261002-01`: CSV в `game`, JSON-планы,
observations, summaries и benchmark в `evidence`, кадры в `user-data/screenshots`.
Сборки и журналы лежат в `G:/SS/lab/build-x64-stage4` и `G:/SS/lab/perf-*.log`.
Проверки: сборка Game/benchmark, byte-parity benchmark для трёх форматов,
прогоны двух карт и двух редакторов, сравнение разрешений и проверка скриншотов.
Тестовые игры завершены штатно.
