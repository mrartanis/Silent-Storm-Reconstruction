# Блокер пути ввода

Обновление после разрешения пользователя 2026-09-22: разрешён альтернативный ввод SendInput или другой необходимый способ. Создан LabInput.cpp (только процессы внутри G:\SS\lab, проверка foreground, относительное движение, scan codes, отдельные down/up). DirectInputProbe с новой опцией exclusive практически получил F7 down/up, dx=10, dy=5 и left-button down/up. Материалы: G:\SS\lab\evidence\sendinput-20260922. Ограничение на альтернативный ввод снято прямым указанием пользователя; предыдущие записи об ожидании разрешения исторические.

Исследование способов ввода 2026-09-22: кандидат для следующего эксперимента — SendInput с MOUSEEVENTF_MOVE без MOUSEEVENTF_ABSOLUTE, отдельными down/up кнопки и KEYEVENTF_SCANCODE для клавиатуры. Microsoft описывает [относительное движение](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-mouseinput), [scan codes](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-keybdinput) и [exclusive mouse](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee416848(v=vs.85)). Это гипотеза подходящего ввода, а не практическая проверка совместимости с нашей игрой.

Готовый кандидат — [PyDirectInput](https://github.com/learncodebygaming/pydirectinput/blob/master/pydirectinput/__init__.py). Проверенный исходник master использует абсолютный путь даже для moveRel по умолчанию; для относительного SendInput требуется `moveRel(dx, dy, relative=True)`. Не выбирать координаты клика по системному указателю: ориентироваться на игровой курсор на снимке, двигаться малыми шагами, отдельно нажимать/отпускать кнопку без перепозиционирования. Сначала проверить события на DirectInputProbe, затем клик меню и клавишу I в игре. Поддержка exclusive режима должна быть подтверждена отдельно; работа обычного Win32 окна этого не доказывает.

Альтернативный инструмент пока не установлен/не запущен: ожидается прямое разрешение пользователя на исключение из guidance computer-use ("Use only the Computer Use JS APIs for Windows app automation."). Поиск способа сам по себе не считается таким разрешением. Захват экрана остаётся через существующий плагин. Никаких правок игрового ввода и алгоритмов в этом эксперименте не требуется.

Дополнение 2026-09-22: пользователь включил аппаратный курсор; `cfg/config.cfg` сохраняет `ui_hwcursor = 1.00`. Новый прогон hardware-cursor-test-01 с этим конфигом повторил блокер: два клика по учебной миссии (162,660 на снимке 1000x750) не переводят в миссию, программная рука остаётся в левом верхнем углу, системный указатель находится над кнопкой. Escape на заставке не дал подтверждённого пропуска. Скриншот, дамп и настройки сохранены в evidence этого прогона.

Статическая причина, почему флажок не помогает в этой сборке: Main/Cursor.cpp:256–258 лишь объявляет и регистрирует bHWCursor; других чтений этой переменной нет. CCursor::Update продолжает интегрировать относительные bindX/bindY, Draw рисует программный курсор. iOptionsMenu только читает/сохраняет ui_hwcursor. Input/Input.cpp:387 задаёт мыши DISCL_EXCLUSIVE | DISCL_FOREGROUND; наличие отладчика исключает из exclusive только устройства, отличные от мыши. Это подтверждает замечание пользователя о захвате мыши. Реализация аппаратного курсора здесь неполная; это отдельный обнаруженный дефект реконструкции, а не ошибка настройки пользователя. Исходники игры не исправлялись в рамках диагностики.

Нужен Windows backend, доставляющий клавиатурные scan codes в DirectInput и корректное относительное движение мыши. Игровые алгоритмы для обхода не менять.
